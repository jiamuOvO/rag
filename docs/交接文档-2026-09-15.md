## 1. 怎么把它跑起来

```powershell
cd F:\RAG\Li_Jia
.\scripts\start.ps1
```

启动脚本会依次**隐藏输入**收：`RAG_CHAT_API_KEY` → `RAG_EMBEDDING_API_KEY` → 管理员密码哈希（首次）→ `RAG_SESSION_SECRET`，然后跑连通性自检，最后 `python -m rag.cli serve`。

### ⚠️ 三条必须知道的运行规则

1. **改 `config.yaml` 必须重启才生效。** `api.py:26` 是**模块级** `pipeline = Pipeline()`，`Settings.load()` 只在进程启动时执行一次 —— 配置在启动那一刻就冻结了。
   铁证：`config.yaml` 改成 120/180 后，未重启的运行仍记 `read=60.0/total=75.0`。
2. **密钥是进程私有的，永远不落盘。** `config.yaml` 只存 `api_key_env`（**变量名**）；`config.py:27-29` **拒绝**明文 `api_key`；`start.ps1` 只把密钥放进自己那个进程的环境变量。
   后果：**任何不走 `start.ps1` 的进程都拿不到密钥** —— `rag.cli evaluate`、本地跑 embedding、本地跑生成，全会退化成 `extractive_demo` 并报 `*_CONFIG_MISSING`。
3. **需要密钥但不想重启服务时，走 HTTP 调已在跑的服务**（它持有密钥）。这是本项目最省事的一条路，评测脚本默认就这么做。
   必须用本地进程时：`.	\scripts\with_model_keys.ps1 "<命令>"`（同样是隐藏输入）。

### 可用性判据

看 **`/ready`**，不是 `/health`。`/health` 只看进程与数据库，未配管理员密码时它照样报 `ok`，而 `/ready=false`、`degraded_components=["auth"]`、管理台全 401。

## 2. 评测体系：**日常只跑端到端**

两层评测，两套测试集，回答两个不同的问题。**产品口径只看第一层。**

| | ① 端到端问答（**日常口径**） | ② 检索排序（按需诊断） |
|---|---|---|
| 测试集 | `tests/eval_cases.yaml`，**8 例** | `tests/retrieval_gold.yaml`，**5 问 / 13 个相关 chunk** |
| 判据 | 5 项布尔：`mode` / `terms` / `scope` / `citations` / **`not_degraded`** | Recall@K / MRR / nDCG@K（HitRate、Precision 也在） |
| 脚本 | `tests/evaluate_http.py` | `tests/retrieval_metrics.py` |

### 命令速查

```bash
# ① 端到端（要额度：每例 1 次真实生成，整轮 8–20 分钟）
PYTHONPATH=src .venv/Scripts/python.exe tests/evaluate_http.py --json var/eval_http.json

# ② 检索指标，三种跑法，按"要不要烧额度"选
PYTHONPATH=src .venv/Scripts/python.exe tests/retrieval_metrics.py                  # 0 调用，只有 BM25 腿
PYTHONPATH=src .venv/Scripts/python.exe tests/retrieval_metrics.py --base-url http://127.0.0.1:8000
PYTHONPATH=src .venv/Scripts/python.exe tests/retrieval_metrics.py --replay var/metrics_http.json   # 0 调用
```

### 三个必须记住的口径坑

1. **`not_degraded` 是我加的，故意的。** 旧的 `rag.cli evaluate` 在无密钥的 shell 里会报 **8/8 全绿**，但每条都是 `degraded=true` + `extractive_demo` —— **模型一次都没调用**。那两个数字**不可直接比较**。
2. **`--replay` 是免费的**：服务把每个候选写进 `query_candidates(retriever, rank)`（`bm25`/`dense`/`rrf`），直接 SELECT 就能拿到三条腿的完整排名，**不需要管理员登录、不需要密钥、不需要重跑**。
3. **金标用 `chunk_id` 做 join 键 → 任何重入库之后必须重跑 `tests/derive_gold.py` 重新推导。**（该脚本默认读 `var/rag.sqlite3`，带缺库与零命中守卫；它以前硬编码读 `tmp/` 副本，副本不在时 sqlite 会**静默建空库并把金标写成空集**。）

PDF 提取层用控制字符顶替符号（`℃`、上标等）。**两种扫描口径的同一事实**：宽口径 **46/258 页、138/929 chunks**，窄口径 **35/258 页、79/929 chunks**（差异来自扫描范围，不是两次不同的污染）。
代码侧已加清洗（`text.py` 的 `CONTROL_OR_ENCODING_RE`）与污染页 OCR 路由，但**没有重入库**，所以 `chunk_id` / `evidence_id` 都没变。
**不要靠"直接删掉字符"伪装成修复。**

## 5. 当前真实状态与已知问题（按优先级）

### 5.1 上游模型服务是唯一的稳定性瓶颈（**最高优先级**）

两台主机，**不是同一台**：

| 用途 | 地址 | 位置 |
|---|---|---|
| chat | `183.162.245.47:11888/v1` | 公网 |
| embedding | `192.168.31.18:7001/v1` | **局域网** |

- **embedding 走局域网** → 网络抖动会直接让检索降级为纯 BM25（`dense=0`），实测连续 6 次 `EMBEDDING_SERVICE_UNAVAILABLE`、每次卡 ~30.9 s。
- **生成耗时 18–180 s，波动极大**；同为 8 例评测，同一批问题在上游劣化期间**整体慢 2–3 倍**（`no_evidence_refusal` 38.7 s → 128.1 s，而这条 evidence=0，根本没有长提示词可言）。
- **失败从来不是答案质量问题**：所有有返回的用例，`mode`/`terms`/`scope`/`citations` **全部通过**，只有 `not_degraded` 是 false。

**已修的设计缺陷**：重试把总预算**切开**了。`providers.py:73-77` 每次尝试取 `read = min(read_timeout, total - elapsed)`，而循环是 `for attempt in range(2)`：

| 配置 | 第 1 次 | 重试 | 真实耗时 140 s |
|---|---|---|---|
| 60 / 75 | 60 s | 15 s | 失败 |
| 120 / 180 | 120 s | 60 s | **失败（180 s 预算够，却被切碎）** |
| **180 / 180** | **180 s** | — | **成功** |

已把 `config.yaml` 改成 `read=180=total`（等价「单次尝试 + 全额预算」，严格不差于平分）。**`total` 没有加大** —— 180 s 这个天花板很可能只是上游变慢的假象。

**重跑评测前先确认两台主机都活着**：

```bash
curl -s -o /dev/null -w "%{http_code}\n" -m 10 http://183.162.245.47:11888/v1/models
curl -s -o /dev/null -w "%{http_code}\n" -m 10 http://192.168.31.18:7001/v1/models
```

两个都返回 `401`（= 有响应）才算上游正常。**上游不稳时跑出来的数字没有意义。**
> 2026-09-14 已经踩过一次：上游中途劣化，端到端跑出 `1/8`，那个数字**不能当基线**。

### 5.2 `chat.timeout_seconds` 是死键

`config.py:102` 把它读进 `settings.chat_timeout_seconds`，但**全仓没有任何消费者**（对照：`embedding_timeout_seconds` 在 `providers.py:177` 有消费者，所以 embedding 的 120 是生效的）。
真正生效的是 **`chat.read_timeout_seconds` / `chat.total_timeout_seconds`**（`config.py:129-130`），也可以用环境变量 `RAG_CHAT_READ_TIMEOUT_SECONDS` / `RAG_CHAT_TOTAL_TIMEOUT_SECONDS`。

### 5.3 `evidence[:5]` 硬编码，窗口调大对提示词无效

`providers.py:105` 的 `answer()` 里是 `evidence[:5]`。`pipeline.py:577` 的 `selected = evidence[:depth["evidence"]]`（现为 8）传给 `answer()` 后，**又被截到 5 条** → 窗口 5→8 时 `selected[:5]` 与原先前 5 条**完全相同，提示词一个字节没变**。
所以「金标排第 6 位就能进模型视野」是**错的 —— 第 6 条永远进不去**。窗口 8 真正影响的是：返回给前端的 evidence 列表、引用校验白名单、`extract_visualization` 的输入。
**要真正扩大模型视野必须改那个硬编码的 5**，但当前瓶颈是生成太慢，**不建议现在动**。

### 5.4 检索性能：97% 的时间花在 SQLite 连接，不是算法

- 检索算法本身约 **25 ms**；单次 query 共开 **8 次** SQLite 连接，热态 **1075 ms**，其中连接开销约 **1040 ms（97%）**；换复用长连接 → **40 ms**。
- 根因：`Store.connect()`（`store.py:260`）每次调用都新建连接、commit、close，而库是 WAL；本机 **F:/D: 盘的 fsync / 目录元数据延迟约 53 ms**，C: 只有 0.5–3 ms。
- 生产 retrieve 阶段 640–880 ms，同量级。**未修。**

### 5.5 其他未修项

- **空证据不短路**：`pipeline.py:523` 只有 `answer_policy == "strict"` 才走拒答短路，而 `models.py:76` 默认 `evidence_first` —— 但按 `evidence_first` 的定义，无证据时应输出「未经当前知识库验证」的通用知识段，**所以这是设计而非缺陷**（上一份记录把它当缺陷，此处更正）。它确实会让空证据问题也等一次完整生成。
- **管理员密码哈希落盘**：`var/admin_password_hash.txt`（`pbkdf2_sha256`，90 B）。已被 `.gitignore` 忽略，但**会进备份快照**（`var/backups/`）。明文不可恢复，换密码的办法是删掉该文件再跑启动脚本。
- **版本漂移**：`pyproject.toml` = 0.4.0，`src/rag/__init__.py` 的 `__version__` 仍是 `"0.2.0"`。
- **评级/工程项**：FIX-01 数据重入库、FIX-05-3 `/v1/logs`、容器透传模型配置、LICENSE + CI、`var/backups` 留存轮转与 jsonl 轮转，**均未做**（见 `审计报告-2026-09-11.md`）。
