# Chat 生成超时诊断（2026-09-15）

## 结论

生成降级发生在远端 Chat 服务返回 HTTP 响应头之前。本地 SQLite、BM25、Dense、Embedding 和 FastAPI 均不是本次超时瓶颈。

当前 Chat 接口为非流式 `/chat/completions`。客户端发送请求后在 `HTTPConnection.getresponse()` 等待；远端完成排队和生成前不会返回响应头，因此页面只能持续显示“正在检索/正在生成”。达到总超时后，Pipeline 返回 `extractive_demo` 作为降级结果。

现有客户端计时可以定位到“等待响应头”，但不能区分远端内部的队列等待和模型推理耗时。精确区分需要远端服务记录 queue time、time to first token 和 generation time。

## 真实复现

测试服务：`http://127.0.0.1:8000`。测试前 `/health=ok`、`/ready=true`，Chat 和 Embedding 均配置完成。旧 `var/logs/rag.jsonl` 已清空，本轮日志不与历史运行混合。

### 超时请求

- request_id：`req_16ecb26441fc469eba3ceffc7c49f5e7`
- 问题：`Compare reported furfural yields from xylose across papers.`
- 本地检索：409 ms
- Embedding：31 ms
- Chat TCP 连接：31 ms
- Chat 总耗时：180.021 s
- `headers_ms`：未产生
- `body_ms`：未产生
- 结果：`CHAT_TIMEOUT`，降级为 `extractive_demo`

`connect_ms` 已产生而 `headers_ms` 未产生，说明连接成功后卡在 `conn.getresponse()`，180 秒内没有收到响应头。

### 正常对照

- request_id：`req_e1607ca14af3481dbf09af5b0817d637`
- 问题：`Which xylose experiment reported 71.1% furfural yield at 130 C?`
- 本地检索：378 ms
- Chat TCP 连接：16 ms
- 等待响应头：59.265 s
- 读取响应体：0 ms
- 结果：正常 `openai_compatible` 回答

正常请求同样把几乎全部时间花在等待响应头。响应头到达后，响应体立即读完。这进一步排除了响应下载速度。

## 已增加的观测

`OpenAICompatibleProvider.last_call` 现在记录：

- `connect_ms`：TCP/TLS 建连耗时；
- `headers_ms`：发送请求至收到响应头的耗时；
- `body_ms`：读取响应体耗时；
- `duration_ms`：整个 Chat 调用耗时，失败时也保留。

自动化回归：`59 passed, 6 warnings`。

## 解决方案

### 1. 先限制损失：90 秒后降级

将 Chat 总超时设为 90 秒，读取超时不重试。实测正常请求为 17.6、37.8、59.3 和 84.3 秒；失败请求超过 180 秒。90 秒能保留本轮观测到的正常响应，同时把最坏等待从 180 秒减半。

这是止损值，不是性能优化。远端继续变慢时仍会降级。

### 2. 限制答案长度

向 Chat payload 增加明确的 `max_tokens`，建议先用 800，并要求回答简洁。当前请求没有输出长度上限；比较类问题还要求模型生成结构化可视化 JSON，可能增加生成时间。

`max_tokens` 可以限制长回答的推理/生成成本，但不能消除远端队列等待。上线前应使用 8 题端到端集比较答案完整率和延迟。

### 3. 改成端到端流式响应

向模型请求发送 `stream=true`，FastAPI 使用 `StreamingResponse` 转发 SSE，前端逐块显示内容并允许取消。这样能够获得真实的 time-to-first-token，也不会让用户长时间只看到固定占位文字。

流式响应改善等待体验和诊断能力，但如果远端连第一个 token 都不返回，仍需要 90 秒总超时和抽取式降级。

### 4. 连续故障时快速降级

当最近一次 Chat 请求超时后，在短时间内直接使用抽取式回答，避免每个用户都重复等待完整超时。单进程部署可用一个进程内时间戳实现；扩展到多进程后再迁移到共享状态。

只有实际出现连续超时后再加这一项，当前不先引入额外状态。

## 建议实施顺序

1. 总超时改为 90 秒，读取超时不重试。
2. 增加 `max_tokens=800`，运行 8 题真实 HTTP 评测。
3. 对比成功率、P50/P95、降级率和答案完整性。
4. 如果用户仍无法接受等待，再实现 SSE 流式响应。

不要替换 BM25、Dense、RRF、SQLite 或 Embedding 服务；本轮数据已经证明它们不在超时链路上。
