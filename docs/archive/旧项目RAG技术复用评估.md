# 旧 RAG 项目技术复用评估

## 1. 评估目的与结论

本文以一套成熟、可维护、可评测的科研论文 RAG 为参照，评估旧项目已有代码的真实可复用程度。评估重点是技术路线、关键参数、工程完整性和科研证据可信度，而不是 PPT 中列出的功能是否实现。

旧项目已经具备通用 RAG 原型的部分基础组件，包括前端界面、FastAPI 服务框架、文档上传、RAGFlow DeepDoc 解析代码、向量生成、Elasticsearch 存储和流式回答。但是，它尚未形成成熟科研 RAG 所需的数据质量控制、稳定检索、严格证据链、领域结构化抽取和评测闭环。

综合判断：

| 能力层 | 估计成熟度 | 主要判断 |
| --- | ---: | --- |
| 前端与应用框架 | 60%–70% | 产品外壳较完整，可作为新项目界面基础 |
| 文档解析基础 | 45%–60% | 技术路线合理，但缺少质量验收和稳定的数据协议 |
| 切块与索引 | 25%–35% | 可以执行基础切块和入库，但参数及元数据设计不足 |
| 检索与重排 | 20%–30% | 存在混合检索代码，实际链路不完整且参数未经评测 |
| 生成与引用 | 20%–30% | 能组织文本回答，但引用不能构成严格科研证据链 |
| 领域结构化抽取 | 0%–10% | 未形成材料、反应、条件、结果等领域数据模型 |
| 自动评测与质量控制 | 约 0% | 没有标准问题集、检索指标或回归测试 |
| 部署与运维 | 10%–20% | 配置不完整，存在缺失模块、密钥和数据一致性风险 |
| 整体成熟度 | 约 25%–35% | 属于可演示原型，不属于成熟科研 RAG |

新项目推荐采用“保留应用外壳与合理基础技术，重建核心数据与检索链路”的方式。不要直接复制整个旧后端后仅替换领域名称。

## 2. 成熟科研 RAG 的参照流程

成熟科研 RAG 至少应形成以下闭环：

1. 文献接入、格式校验、内容哈希去重和版本管理。
2. 文本层提取、OCR、版面分析、阅读顺序恢复、表格与图片解析。
3. 解析质量检测，并标记低置信度、乱码、缺页和结构异常。
4. 按章节、段落、实验步骤、图注和表格进行结构感知切块。
5. 抽取领域实体、关系、反应条件和实验结果。
6. 完成实体归一、单位归一、数值校验和冲突检测。
7. 将文本、向量、结构化数据及原始证据分别写入适合的存储系统。
8. 对用户问题进行分类、改写、实体识别和过滤条件解析。
9. 联合执行关键词、向量、元数据及结构化查询，并融合、去重和重排候选证据。
10. 根据 token 预算组织上下文，只基于证据生成答案；证据不足时明确拒答。
11. 将答案中的关键声明绑定到页码、章节、图表和原文位置。
12. 使用标准问题集持续评测解析、召回、重排、答案和引用质量。
13. 记录任务状态、阶段耗时、错误位置、模型版本和索引版本，以支持定位和回归。

旧项目覆盖了其中若干基础节点，但第 3、5、6、8、10、11、12、13 项基本缺失或不完整。

## 3. 可以直接复用的部分

这里的“直接复用”指技术选择和工程结构可以作为新项目底座。复用时仍需整理依赖、配置和许可证，不代表逐文件原样复制。

### 3.1 前端工程和交互框架

- React/Vite 工程结构。
- 登录、首页、知识库、聊天和历史会话页面的布局基础。
- 流式 SSE 回答的交互形式。
- 文档上传、消息展示、来源列表和引用抽屉等通用组件。
- API 请求封装、路由和状态管理方式。

这些能力与具体研究领域耦合较低，适合作为新项目前端基础。旧项目未完成的按钮或接口仍需逐项验证，不能把已有 UI 当成对应能力已经实现。

### 3.2 后端应用分层方式

- FastAPI 的路由、Schema、Service 和 Model 分层思路。
- 正式知识库上传与临时文档问答分开的产品设计。
- 流式响应接口。
- 环境变量承载可变配置的原则。

旧代码的具体异常处理和数据事务不可直接照搬，但整体服务组织方式合理。

### 3.3 存储技术组合

- PostgreSQL 保存用户、会话、文档登记和结构化业务数据。
- Redis 保存短期任务状态、缓存或临时会话内容。
- Elasticsearch 同时承担 BM25、向量检索、元数据过滤、高亮和聚合。
- 文件系统或对象存储保存原始 PDF、页面图、表格和图片。

对于第一版及中等规模科研语料，Elasticsearch 足以同时承担关键词和向量检索，没有必要仅为了架构形式额外引入 Milvus。只有规模、成本或性能测试证明 ES 不够时，才需要独立向量数据库。

### 3.4 模型适配协议

采用 OpenAI 兼容客户端的思路可以保留，但必须理解为“统一接口协议”，而不是绑定 OpenAI 模型。DeepSeek、通义千问、部分国内推理服务、Ollama 代理和自建兼容服务都可以通过适配层接入。

新项目应在业务代码与模型 SDK 之间建立独立接口，例如 EmbeddingProvider、RerankProvider 和 ChatProvider。业务链路不能直接依赖某个供应商的 SDK、模型名或返回字段。

### 3.5 文档解析技术路线

- 使用文本层提取与 OCR 结合，而不是仅调用简单 PDF 文本提取。
- 使用版面识别恢复双栏、标题、正文、表格和图片区域。
- 使用表格结构识别和文本框上下关系合并。
- 保留页码、坐标和非文本对象的设计方向。

RAGFlow DeepDoc 的总体路线适合科研论文，可作为解析引擎候选。是否作为最终解析器，需要使用目标论文进行质量评测。

## 4. 需要修改后复用的部分

### 4.1 DeepDoc 解析实现

旧项目保留了 RAGFlow/InfiniFlow 的解析、OCR、版面和表格代码，这些代码具有利用价值，但不能作为黑盒直接接入生产链路。

需要修改：

- 固定上游版本、模型版本和许可证信息。
- 补齐可复现依赖，禁止运行时无记录地下载模型。
- 定义统一解析输出，至少包含 paper_id、page、block_id、block_type、section_path、text、bbox、reading_order、object_id、parser_version 和 OCR confidence。
- 增加双栏顺序、页眉页脚、跨页段落、图注绑定、表格单元格、公式、上下标和化学式的专项处理。
- 增加低质量解析检测和降级路线，例如文本层失败后才启用 OCR。
- 为解析器升级建立固定论文集回归测试。

### 4.2 切块策略

旧项目的 `naive_merge` 可以保留为基线算法，但不能继续把 128 token 作为默认生产参数。

需要修改：

- 优先按照章节、段落、完整实验步骤、图注和表格边界切块。
- 对超长结构块再按 token 限制拆分。
- 增加 overlap，避免实体、条件和结果在边界处分离。
- 建立父子块关系：子块用于精确检索，父块用于补充生成上下文。
- 保存 previous_chunk_id、next_chunk_id、parent_chunk_id 和 section_path。
- 表格同时保留完整表格表示和行级表示；图注与对应图片保持绑定。
- 使用目标论文比较 256、384、512 token 及结构感知切块，不预设唯一最佳值。

### 4.3 Embedding 调用

DashScope `text-embedding-v3`、1024 维可以作为第一轮 baseline，不能在没有评测的情况下认定为最终模型。

需要修改：

- 模型、服务地址、维度和批大小全部配置化。
- 校验每批返回数量、向量类型和向量维度。
- 请求失败时进行有限重试和指数退避。
- 单条失败必须记录状态，禁止用 `None` 继续入库或通过 `zip` 静默丢弃切片。
- 保存 embedding provider、model、dimensions 和 index_version。
- 更换模型或维度时创建新索引，不得混用不同向量。
- 对已生成向量进行内容哈希缓存。
- 使用目标问题评测中文提问检索英文论文、化学缩写和精确数值的效果。

### 4.4 Elasticsearch mapping 和索引结构

Elasticsearch 可以保留，但现有动态后缀 mapping 与文档字段设计需要重建。

需要修改：

- 明确定义 paper、chunk、table、figure 和 evidence 的字段协议。
- 使用文件内容哈希或稳定文献标识生成 paper_id，不能只哈希文件名。
- chunk_id 必须包含文档版本和稳定位置语义。
- 明确索引 analyzer、vector dimensions、相似度函数和过滤字段。
- 保存 page、section、bbox、object reference、parser version、embedding version 和 source hash。
- 对写入执行数量校验，并确保数据库登记、文件保存和 ES 入库具有一致任务状态。
- 避免 PostgreSQL 已显示成功而 ES 实际为空的假成功状态。

### 4.5 混合检索

关键词检索、Dense retrieval、元数据过滤和候选融合的方向正确，但旧项目参数来源于上游默认配置，缺少本项目评测依据。

需要修改：

- 分开测量 BM25、Dense、BM25 + Dense 和加入 reranker 后的表现。
- 优先测试 Reciprocal Rank Fusion，避免直接线性相加未经校准的异构分数。
- 对化学品名称、缩写、分子式、DOI、温度、数值和单位加强精确匹配。
- 保留用户指定的文档范围；空结果时不得静默移除 doc_ids。
- 召回结果进行内容去重、相邻块合并和文档多样性控制。
- 根据问题类型使用不同检索路径，精确条件查询不能只依赖向量相似度。

### 4.6 Reranker

使用专用 reranker 对初召回候选进行二次排序是合理路线，DashScope reranker 可以作为一个可替换实现。

需要修改：

- 限制候选数量和单条文本长度。
- 记录重排前后排名、分数、模型版本和耗时。
- 设定明确的失败降级状态，不能静默退化而无法观测。
- 使用 Recall@K、MRR、nDCG、延迟和费用对比有无 reranker。
- 重排后只选择满足证据阈值和上下文预算的少量候选。

### 4.7 上传、任务和错误处理

上传入口可以复用，但同步解析和宽泛异常捕获不适合成熟系统。

需要修改：

- 校验文件名、MIME、文件头、大小、加密状态和内容哈希。
- 防止文件名路径穿越。
- 大文件流式保存，避免一次性全部读入内存。
- 上传与解析分开，解析通过任务队列执行。
- 任务状态至少包含 queued、parsing、chunking、embedding、indexing、ready 和 failed。
- 每次运行分配 run_id，每个阶段记录开始时间、结束时间、耗时和错误码。
- 使用结构化日志，而不是散落的 print。
- 错误必须向上返回并写入任务状态，不能捕获后伪装成成功。

为了便于快速定位且不明显降低速度，应默认记录阶段级结构化日志和耗时；详细 trace、原始模型请求及逐块调试信息只在诊断模式开启，或进行低比例采样。

### 4.8 生成与引用展示

流式生成和引用 UI 可以保留，生成逻辑与引用算法必须重建。

需要修改：

- Prompt 明确区分系统指令、用户问题和不可信文档内容。
- 只允许基于已提供证据回答。
- 上下文不足时返回证据不足，而不是退化为普通模型自由回答。
- 数值必须连同对象、条件和单位返回。
- 上下文在进入模型前去重、排序并限制 token。
- 引用必须来源于检索阶段的稳定 evidence_id。
- 前端展示页码、章节、图表编号、原句或表格行，并支持回看原 PDF。

## 5. 必须补充的部分

### 5.1 生物质与呋喃领域 Schema

旧项目没有可以直接迁移的领域数据模型。新项目需要根据目标论文建立至少包含以下概念的 Schema：

- 论文及其版本。
- 生物质原料、糖类底物及组成。
- 预处理和分级过程。
- 催化剂、活性组分、载体和催化剂用量。
- 溶剂、双相体系和添加剂。
- 目标呋喃化合物、伴生产物和副产物。
- 温度、时间、压力、气氛、反应器和能量输入方式。
- 转化率、收率、选择性、生产率和碳平衡。
- 催化剂循环和失活。
- 反应路径、机理与证据。

最小结构化单位应优先采用“一条实验或反应记录”，而不是仅采用“一篇论文”或“一个样品”。

### 5.2 实体和单位归一

需要补充：

- 化合物规范名、简称、同义词、分子式、CAS 和可选 SMILES 映射。
- HMF、5-HMF、5-hydroxymethylfurfural 等别名统一。
- 催化剂缩写与完整组成对应。
- 生物质名称及组成分类。
- 温度、时间、压力、浓度、质量比、摩尔比和性能指标单位转换。
- 原始值与标准值同时保存，禁止单位转换后丢失原文。
- 对 conversion、yield 和 selectivity 进行语义区分，不能仅因为数值单位相同而混用。

### 5.3 结构化抽取与校验

需要建立“候选定位—结构化抽取—归一—校验—人工复核”的可审计流水线：

- 候选定位优先覆盖实验部分、表格、图注和结果讨论。
- LLM 或规则输出必须符合 JSON Schema。
- 每个字段绑定 evidence_id。
- 校验数值范围、单位、对象、条件和指标类型。
- 检测正文、表格和补充材料中的冲突。
- 保存抽取模型、Prompt、Schema 和运行版本。
- 低置信度与冲突字段进入人工复核队列。

### 5.4 Query Router 与结构化查询

需要区分：

- 单篇论文事实问答。
- 精确数值查询。
- 条件筛选和排序。
- 跨论文比较。
- 机理解释。
- 表格或图片定位。
- 数据缺失判断。

涉及收率、温度、催化剂和筛选条件的问题应优先查询结构化数据库，再使用文本证据解释；机制类问题更适合文本混合检索。

### 5.5 严格证据链

每条关键事实至少需要关联：

- paper_id 和 DOI。
- page 和 section。
- figure/table/caption 标识。
- 原文或表格单元格。
- bbox 或对象坐标。
- extraction_run_id。
- 置信度与人工确认状态。

旧代码通过回答句子与 chunk 的语义相似度补引用，只能表明文本相似，不能证明来源支持该声明。新项目不能把这种算法作为科研引用依据。

### 5.6 拒答与冲突处理

必须补充：

- 未召回可靠证据时明确拒答。
- 证据只能支持部分问题时区分已知与未知部分。
- 多篇论文或同一论文出现不一致数据时同时呈现并说明条件差异。
- 不能把没有报告解释成数值为零。
- 用户限定论文范围时，不能自动扩大到其他文献。
- 检索、模型或解析服务失败时，不能返回看似正常的自由生成答案。

### 5.7 评测集与回归测试

需要补充：

- 代表性正常文本 PDF、双栏 PDF、图表密集 PDF 和扫描 PDF。
- 人工标注问题、标准答案、正确证据页和相关 chunk。
- 解析指标：阅读顺序、文本覆盖、表格单元格、图注绑定和 OCR 准确性。
- 检索指标：Recall@K、MRR、nDCG 和错误类型。
- 生成指标：faithfulness、答案完整性、数值与单位准确率。
- 引用指标：citation precision、citation recall 和声明覆盖率。
- 结构化抽取指标：字段 precision、recall、F1 和证据正确率。
- 工程指标：解析耗时、检索延迟、生成延迟、失败率、重试率和资源峰值。
- 固定回归集，保证切块、模型、Prompt 和索引升级后不发生静默退化。

### 5.8 可观测性和版本管理

为了做到报错后快速定位，同时避免明显影响运行速度，应补充：

- request_id、run_id、paper_id、chunk_id 和 model_call_id 的关联。
- 阶段级结构化日志与错误码。
- 各阶段耗时、输入数量、输出数量和失败数量。
- 解析器、Schema、Prompt、Embedding、reranker、生成模型和索引版本。
- 健康检查与依赖状态检查。
- 默认关闭逐 token、逐块全文日志，诊断模式下按需开启。
- 指标异步聚合，日志输出不阻塞主要问答链路。
- 敏感字段脱敏，禁止记录 API Key、Authorization header 和完整模型密钥配置。

## 6. 现有参数与阈值审计

| 参数或行为 | 当前值/方式 | 判断 | 新项目处理建议 |
| --- | --- | --- | --- |
| 切块长度 | 128 token | 对化学论文通常偏小，容易拆开底物、条件和结果 | 对比 256/384/512 与结构感知切块，以评测决定 |
| overlap | 未形成明确机制 | 容易在边界丢失上下文 | 增加可配置 overlap，并保存相邻块关系 |
| 父子块 | 缺失 | 精确召回与完整上下文无法兼顾 | 增加 child retrieval + parent context |
| Embedding 维度 | 1024 | 可作为 baseline，本身没有明显问题 | 与模型版本绑定，禁止不同维度混入同一索引 |
| Embedding 批量 | 最大 10 | 若受服务商限制则合理 | 配置化，并加入返回数量及失败校验 |
| KNN top-k | 1024 | 对当前小规模语料明显偏大 | 首召回从 30–100 范围评测，不硬编码 |
| 重排候选数 | 至少 128 | 可能造成不必要的延迟和费用 | 按 Recall/延迟曲线选择候选数 |
| 相似度阈值 | 0.1 | 对 cosine 通常过低，过滤作用有限 | 使用正负样本分布校准，不直接照搬 |
| 空结果阈值 | 0.1 调为 0.17 | 若为相似度下限，实际变得更严格，与“放宽”意图矛盾 | 修复逻辑，并对空结果使用明确降级策略 |
| 首召回权重 | 关键词 0.05，向量 0.95 | 对化学名、缩写、分子式和数值过度偏向向量 | 优先评测 RRF 或提高 lexical/entity 影响 |
| 二次融合权重 | 关键词约 0.7，向量约 0.3 | 与首召回方向相反，且没有项目评测依据 | 统一评分定义并通过离线实验确定 |
| 引用初始阈值 | 0.63 | 文本相似度不能证明证据支持 | 引用由 evidence_id 产生，不靠答案后匹配 |
| 引用降级阈值 | 逐步降至约 0.3 | 为了产生引用而降低门槛，容易附错来源 | 不允许为保证有引用而降低真实性门槛 |
| 空结果处理 | 移除 doc_ids | 会突破用户限定的论文范围 | 保留显式范围并返回该范围内无证据 |
| 可用状态过滤 | available_int=1 | 入库代码未写该字段，可能导致零召回 | 统一 Schema，并用集成测试验证写入与过滤 |
| 临时 PDF | 最多 4 页 | 不适合完整科研论文 | 改为任务化解析和可配置文件限制 |
| 临时文本 | 最多 4000 字符 | 不适合论文级问答 | 按文件大小、页数和资源预算配置 |
| Redis TTL | 2 小时 | 属于产品策略而非算法问题 | 配置化，区分任务状态、缓存和临时文档 |

所有检索阈值、融合权重和候选数量必须通过目标论文及真实问题评测确定。不能因为参数来自 RAGFlow 上游代码就默认适合生物质与呋喃领域。

## 7. 旧项目的工程风险

### 7.1 交付包不完整

旧项目代码引用了交付包中不存在的运行模块，例如检索入口、数据库操作和密码工具；同时缺少完整后端 Dockerfile、Python 依赖清单及锁文件。因此当前目录不能作为可从零复现的完整交付物。

### 7.2 异常被吞掉并产生假成功

部分解析、Embedding 和 ES 写入代码捕获异常后只打印或返回空结果，没有继续向上传接口传播。上层可能继续登记数据库成功，形成“数据库显示已上传、ES 实际没有切片”的不一致状态。

### 7.3 数据库定义不一致

ORM 模型与初始化 SQL 在消息字段、时间字段和文档上传表等方面不一致。不同启动方式可能得到不同数据库结构，导致运行时查询失败。

### 7.4 标识符不稳定

文档 ID 主要根据文件名生成，不能区分同名不同内容、内容更新和不同版本。切片 ID 也没有完整包含文档版本及位置语义，不适合证据长期引用。

### 7.5 敏感配置风险

旧代码包含默认密钥、明文数据库或检索服务密码以及硬编码外部服务 token。任何旧 token 都应视为已经泄漏并撤销。新文档和新代码不得复制或记录具体密钥值，所有凭据必须通过未提交的环境变量或密钥管理系统注入。

### 7.6 缺少测试和运行说明

旧项目没有形成完整的单元测试、集成测试、检索评测、标准问题集、CI、后端依赖锁定和可复现演示步骤。能在原开发环境演示不能证明交付包可部署或检索质量达标。

### 7.7 许可证与来源管理

解析和检索模块中存在 RAGFlow/InfiniFlow Apache 2.0 代码。新项目复用时需要保留相应版权和许可证声明，记录上游版本，并明确自研代码与第三方代码边界。

## 8. 新项目推荐复用策略

### 8.1 保留

- 前端产品外壳和通用交互组件。
- FastAPI 服务分层和 SSE 响应形式。
- PostgreSQL、Redis、Elasticsearch 的基础组合。
- Elasticsearch 混合检索能力。
- DeepDoc 作为候选解析引擎。
- 模型供应商可替换的协议适配思想。

### 8.2 重建

- paper、block、chunk、object 和 evidence 的统一数据协议。
- 稳定 ID、内容哈希、版本和任务状态体系。
- 结构感知切块与父子块。
- 领域实体识别、同义词和单位归一。
- Query Router、混合召回、候选融合与重排配置。
- 结构化反应数据及精确查询路径。
- 逐声明证据绑定、拒答与冲突处理。
- 离线评测、回归测试和轻量可观测性。

### 8.3 第一版实施原则

- 先用代表性论文建立解析和检索 baseline，不先追求完整产品功能。
- Embedding、reranker 和生成模型均通过适配层接入，不绑定单一供应商。
- 每个阶段都产出可检查的中间状态，失败时可通过 run_id 定位具体阶段。
- 默认只记录结构化摘要指标，详细诊断按需开启，避免可观测性显著拖慢主链路。
- README 必须区分：已验证能力、仅用于跑通的 demo 方法、后续需要优化的部分和当前仍缺失的部分。
- 在问题集和目标数据表尚未确定前，不宣称任何切块参数、阈值或模型已经达到最佳效果。

## 9. 最终判断

旧项目最有价值的资产是应用外壳、通用解析代码和基础技术组合，而不是现有检索参数或专业数据能力。

可以直接沿用的是低领域耦合的框架和技术方向；需要修改的是解析输出、切块、Embedding、索引、检索、重排、上传和生成；必须补充的是生物质与呋喃领域 Schema、实体与单位归一、结构化抽取、可信证据链、拒答、评测和可观测性。

新项目不应复制整个旧后端再逐步修补。更稳妥的做法是以旧项目前端和部分通用组件为参考，重新建立一条数据协议明确、错误可定位、参数可评测、证据可复核的科研 RAG 链路。
