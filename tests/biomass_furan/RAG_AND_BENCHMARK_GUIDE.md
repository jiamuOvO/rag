# 第一部分：这套 RAG 系统是做什么的

## 1.1 它解决的问题

一个做生物质转化的研究者，手上有 51 篇论文。他想知道：

> 「2019 年那篇 SnCl4/EMIMBr 的研究里，木聚糖在 130°C 反应半小时，糠醛收率是多少？」

传统做法：打开论文、翻到对应章节、找表格和正文里的数字。51 篇论文，每篇几十页，**找一个具体数值可能花十几分钟**，而且容易漏掉相关论文里的对照数据。

这套系统的目标：**把这个过程压缩成一句话提问**。

提问之后，系统返回的不是一段"看起来像答案"的话，而是**标注了出处的原文摘录**——告诉你是哪一篇论文、第几页、原文怎么写的。用户可以点回去核对。

## 1.2 它刻意不做的事

系统明确不承担"替用户下结论"的角色：

- 如果文献库里没有相关证据，系统会**明确拒答**，而不是用模型自己的知识编一个答案
- 如果用了模型通用知识（非文献库内容），答案里必须带一行显眼的标注，说明这部分**未经当前知识库验证**
- 每一条事实性陈述都必须绑定到具体的证据编号，**引用不出来的结论不允许出现**

这套约束是为了科研场景的可追溯性 —— 用户需要知道每个数字是从哪来的。

## 1.3 核心组成部分

系统由六个部分构成：

| 组成 | 作用 | 通俗说明 |
|---|---|---|
| **文献库** | 存放已解析的论文内容 | 51 篇论文 → 929 页 → 切成 5,444 个文本块，每块存原文和一个语义向量 |
| **解析与切分** | 把 PDF 变成可检索的文本 | 处理扫描件（需 OCR）、乱码字符、按语义把长文切成大小合适的块 |
| **检索引擎** | 找出最相关的文本块 | 关键词检索 + 语义检索两路并行，再把两路结果合并排序 |
| **答案生成** | 把命中的原文组织成回答 | 只把检索到的原文交给语言模型，并要求它标注每条结论的出处 |
| **质量守门** | 拦截不可信的答案 | 校验引用是否有效、证据不足时触发拒答、标记有问题的页面 |
| **交互与运维** | 给用户和管理员用 | 网页问答界面、管理后台、运行日志与性能统计 |

## 1.4 两条工作流程

### 流程一：文献入库（把论文变成可检索的块）

```
扫描论文文件
   ↓
检查是否已经入库过（按文件内容指纹去重）
   ↓
逐页提取文字
   ├─ 正常页 → 直接取文本
   ├─ 扫描页（字符太少）→ 整页 OCR 识别
   └─ 乱码页 → 只对出问题的局部做 OCR 修复
   ↓
按段落和标题结构切分成块（每块约 384 个词单位，相邻块留 64 个单位重叠）
   ↓
为每个块生成语义向量
   ↓
写入数据库
```

**入库质量的三个状态**：完全正常 / 部分页面有问题但正文仍可检索 / 整篇失败。有问题的页面会被单独标记，不会当作正常内容使用。

### 流程二：问答（把问题变成带出处的答案）

```
用户提问
   ↓
理解问题（比如"糠醛收率"会被自动扩展出对应的英文术语）
   ↓
两路并行检索
   ├─ 关键词检索（精确匹配术语和数值）
   └─ 语义检索（按意思相近程度匹配）
   ↓
两路结果合并排序
   ↓
（可选）二次精排
   ↓
把最相关的若干条原文交给语言模型组织答案
   ↓
校验答案里的每条引用是否真实存在于证据中
   ↓
返回答案 + 证据列表（含论文名、页码、原文摘录）
```

**降级机制**：如果语义检索服务不可用，系统会退回纯关键词检索，并在结果里标明"已降级"，而不是假装一切正常。

# 第二部分：为什么需要测评集

## 2.1 核心问题

系统"感觉能用"和"确实好用"是两件事。要回答**「检索这一环到底好不好」**，必须有一个客观的考卷。

## 2.2 测评的对象是什么（重要边界）

**这套测评只衡量"检索"这一环，不衡量"答案生成"的质量。**

原因：最终答案里混了语言模型的发挥。想定位问题到底出在"没找到资料"还是"表达得不好"，必须把它们拆开。检索是上游，如果该找的块没被找出来，后面再好的模型也救不了。

具体地说，测评回答的是：

> 对每一道题，**应该被找到的那些文本块，有没有被系统排到前面来？**

## 2.3 测评的三要素

| 要素 | 内容 | 是否已固定 |
|---|---|---|
| **固定的题库** | 60 道题，覆盖多种问法和难度 | ✅ 已冻结 |
| **固定的资料库** | 官方可检索的 48 篇论文、5,066 个文本块 | ✅ 已冻结 |
| **标准答案** | 每个文本块对每道题的相关程度 | 🔄 构建中 |

标准答案（行业术语叫 **qrels**）是全部工作量所在，也是下面第三部分的主题。

# 第三部分：测评集是怎么构建的

## 3.1 数据来源

| 数据 | 来源 | 数量 |
|---|---|---|
| 文献库 | 系统生产库中**官方作用域**下可检索的内容 | 48 篇 / 5,066 块 |
| 原始论文 | 51 篇 PDF（含扫描件、期刊论文、补充材料） | 929 页 |
| 题库 | 基于文献库中的真实证据**反向设计** | 60 道 |

**题库的设计方法**：不是凭空想问题，而是先在文献里找到一个**具体的、可验证的事实**（比如"某实验在 130°C 下得到 41.7% 收率"），再围绕这个事实设计提问方式。这样每道题天然带着"标准答案依据"，不会出现"题目本身就有歧义"的情况。

## 3.2 筛选标准

**文献纳入标准**：
- 属于生物质转化 / 呋喃化学领域
- 文本内容可被正常提取（扫描件经 OCR 处理）
- 通过页面质量检查（无控制字符污染，或有污染但已完成局部修复）

**文献排除标准**：
- 整篇提取失败（如空文档、加密文档）
- 正文只剩参考文献等无实质内容的页面

> 注：库里有 5,444 个块，但只有 5,066 个进入评测语料。差的部分是**页面质量不合格**的论文（主要是 OCR 或字体映射问题导致的乱码）。这个筛选是**页面级**的，不是简单地把整篇论文删掉。

## 3.3 样本构成（60 道题）

### 按语言

| 语言 | 数量 |
|---|---|
| 中文 | 42 |
| 英文 | 18 |

**设计意图**：真实用户中英文都会问，而系统内部两套语言的处理路径不同（中文需要术语扩展、英文依赖字面匹配），必须分别覆盖。

### 按难度

| 难度 | 数量 | 特征 |
|---|---|---|
| 简单 | 18 | 单一事实，一个文本块就能回答 |
| 中等 | 30 | 需要理解条件组合，或需要区分相近概念 |
| 困难 | 12 | 需要跨文献综合，或多步推理 |

### 按用途分区

| 分区 | 数量 | 用途 |
|---|---|---|
| 开发集 | 12 | 调试和调参时可以随便看 |
| 固定测试集 | 36 | **调参时不许看**，用来做最终客观评价 |
| 挑战集 | 12 | 最难的题，用来观察系统天花板 |

**设计意图**：开发集和测试集分开，是为了防止"针对测试集调参"这种自欺欺人的做法。挑战集单独分开，是因为它们的失败率天然就高，混进平均值会掩盖真实水平。

### 按题型（10 类）

| 题型 | 数量 | 考察什么 | 举例 |
|---|---|---|---|
| 基础事实 | 9 | 能否直接定位到某个具体信息 | 「某研究采用什么方法分离 CMF？」 |
| 条件参数 | 9 | 能否准确提取实验条件组合 | 「优化实验的温度、时间、催化剂用量各是多少？」 |
| 反应机理 | 9 | 能否找到解释"为什么"的段落 | 「为什么锡盐用量不能一味增加？」 |
| 定义概念 | 6 | 能否找到术语的确切定义 | 「该论文如何定义纤维素的单体和连接键？」 |
| 数据数值 | 6 | 能否定位到具体数值 | 「两种配体对应的收率分别是多少？」 |
| 对比分析 | 6 | 能否找到对照实验的数据 | 「两者对收率分别有什么作用？」 |
| 多文档综合 | 6 | 能否跨多篇论文找证据 | 「比较两项研究的催化剂策略」 |
| 条件约束 | 3 | 能否在限定条件下找到匹配证据 | 「限定不外加催化剂，采用什么条件？」 |
| 语义改写 | 3 | 换一种说法还能不能找到 | 「呋喃甲醛」代替「糠醛」 |
| 无答案 | 3 | **资料库里确实没有时，系统会不会硬答** | 「是否报告了某装置 2025 年的实际运行成本？」 |

**设计意图**：
- **条件参数类占比高**（9 道），因为这是科研场景最刚需、也最容易出错的一类 —— 把收率和转化率搞混、把 wt% 和 mol% 搞混都是常见错误
- **语义改写只有 3 道**，因为这类题专门测试"不含原文字面"的情况，是判断语义检索有没有价值的关键
- **无答案题是"陷阱题"**：正确答案是"文献库中不存在"。如果系统硬凑出一个答案，说明它的拒答机制失效 —— 这在科研场景里是最危险的失败模式

### 每道题携带的信息

- 问题原文
- 题型、难度、语言、分区标签
- **必须覆盖的事实**（回答这题至少要说到哪几点）
- 参考答案
- **出题时的种子证据**（当初是依据哪个文本块设计这道题的）

## 3.4 标准答案（qrels）的定义方式

### 四级相关度量表

| 等级 | 含义 | 判定标准 |
|---|---|---|
| **3 级** | 精确命中 | 这一个块**单独**就能给出问题所需的全部或大部分事实 |
| **2 级** | 必要证据 | 含必要的直接证据，但要和其他块拼起来才能完整回答 |
| **1 级** | 背景相关 | 讨论同一研究对象/体系/论文的相邻内容，提供背景、对照或方法，但本身不含所问证据 |
| **0 级** | 无关 | 与该问题主题不同（不同化学品、不同工艺、不同领域） |

**这套量表与 TREC（信息检索领域的国际标准评测会议）以及学术界通用的 UMBRELA 标注体系一致**，便于横向比较。

### 判定流程（保证一致性）

标注时必须**按顺序**回答两个问题：

```
问题一：这个块讲的是不是本题涉及的对象 / 体系 / 论文？
    ├─ 不是，换了研究主题          → 0 级
    └─ 是（同论文 / 同体系 / 同原料）→ 继续
              ↓
问题二：块里有问题所问的具体事实或数值吗？
    ├─ 有，一个块就能回答    → 3 级
    ├─ 有，但需要组合        → 2 级
    └─ 没有，只是背景/对照   → 1 级
```

**为什么要有这个流程**：最初的标注尝试把分级简化成了"有没有答案"的二分类，结果 135 个块里 133 个被判 0 级、**1 级一个都没有** —— 同一篇论文的相邻实验全部被打成"无关"。加入这个两级提问流程后，1 级从 0 个变成 89 个，分布才合理。**分级标注的关键不在于定义写得多清楚，而在于给出每个等级的边界例子。**

### 容易混淆的边界（标注时的强制区分）

| 必须区分 | 原因 |
|---|---|
| 糠醛 / 羟甲基糠醛 / 氯甲基糠醛 / 乙酰丙酸 | 是四种不同化学品，常在同一篇论文里同时出现 |
| 木糖 / 木聚糖 / 葡萄糖 / 果糖 | 不同原料，收率不可互换 |
| 收率 / 选择性 / 转化率 | 三个不同的实验指标 |
| wt% 与 mol% | 量纲不同，不能直接比较 |
| 理论预测值与实验测量值 | 性质不同，不能混用 |

### 证据引用要求

判为 **2 级或 3 级**的，必须摘录**该块内部的连续原文**作为依据。不允许：
- 从论文其他页面借用文字
- 凭已有知识补写
- 引用不存在的句子

这条约束会在校验阶段**逐字比对**，编造的引用过不了检查。

## 3.5 关键的规模决策：为什么不逐块全判

### 两个方案

| | 全量判定 | **Pooling（本方案）** |
|---|---|---|
| 每题要看多少块 | 5,066（资料库全部） | 137（检索系统推出来的） |
| 总判断量 | 303,960 | **8,252** |
| 完整性 | 完备 | 池外未判断 |
| 行业地位 | 理论最强 | **TREC 自 1990 年代起的标准做法** |

### 全量判定为什么不可行

TREC 官方文档记录过：80 万篇文档的语料，逐篇判定每题需要约 **6,500 小时**（按每条 30 秒计）。这就是 TREC 发明 pooling 的原因 —— 它不是取巧，是被现实逼出来的标准解法。

### Pooling 的具体做法

```
第 1 步：让多个检索系统各自对每题返回前 80 名的候选
第 2 步：把这些候选合并、去重，得到该题的"候选池"
第 3 步：只标注池内的块
第 4 步：池外的一律记为"未判断"
```

**为什么这样做是合理的**：如果一个块真的能回答某道题，它大概率会被某个检索系统排进前 80 名。漏掉的可能性存在，但 TREC 三十年的研究表明 —— **这种遗漏对所有被比较的系统是一视同仁的，不影响"哪个系统更好"这个结论**。

### 本项目的池参数

| 来源 | 深度 |
|---|---|
| 真实检索运行 · 关键词路 | 前 80 名 |
| 真实检索运行 · 语义路 | 前 80 名 |
| 真实检索运行 · 融合路 | 前 20 名 |
| 隔离对照组 · 关键词路 | 前 80 名 |

**合并去重后：每题 107–161 条，合计 8,252 对。**

> 需要区分两个"前多少"：**池深度（80）** 决定标注哪些块；**评测截断（20）** 决定算分时只看前几名。两者用途不同。

### Pooling 的代价（必须随结果一起披露）

- 池外的组合**永远不会被判断**，评测时按"不相关"处理
- 后果：**召回率会偏高**（因为分母少算了潜在的相关块）
- 缓解：池深度挖到 80 名；且所有对外报告必须注明"采用 pooling 方法，池深度 80"

## 3.6 标注方式

| 项 | 说明 |
|---|---|
| 标注主体 | **AI 辅助标注**（由语言模型逐块判断） |
| 标注依据 | 固定规范文档，内容包含四级量表、判定流程、边界示例、引用要求 |
| 输出格式 | 结构化的逐条判断记录（题目、块编号、等级、引用原文、判定理由） |
| 覆盖要求 | 每题池内的**每一个块**都必须给出等级，不允许跳过或用"其余都无关"概括 |
| 复核状态 | **尚未进行**独立复核；**人工验收未完成** |

**必须诚实说明的三点**：

1. 这是 **AI 标注**，不是领域专家标注
2. 同模型复核**不等于**双人独立标注，因此**不能报告人工一致性指标**
3. 当前成果只能称为**"AI 候选版"**，距离可正式发布的基准还有距离

## 3.7 已有的人工与模型判断

在本次构建之前，已经存在 351 条判断：

| 来源 | 条数 | 性质 |
|---|---|---|
| 出题时核验的种子证据 | 99 | 其中 2 级 17 条、3 级 82 条 |
| 早期模型批次 | 252 | 全部 0 级 |

**这 351 条里有 241 条不在本次的候选池内** —— 必须保留，不能因为"不在池里"就丢弃。

其中最有价值的是那 99 条种子正例：**它们不在池里，说明检索系统没能把它们召回**。这恰恰是评测要暴露的问题，丢掉就等于掩盖了系统缺陷。

# 第四部分：测评的执行与评分

## 4.1 检索运行的参数

| 参数 | 设定值 | 说明 |
|---|---|---|
| 每题执行次数 | 3 次 | 取中位数，抵消偶发抖动 |
| 预热请求 | 20 次 | 排除冷启动影响 |
| 并发数 | 1（串行） | 避免并发干扰延迟测量 |
| 单次超时 | 120 秒 | 超时记为失败 |
| 随机种子 | 固定值 | 保证可复现 |
| 每种配置的候选导出深度 | 80 名 | 既用于建池，也用于诊断 |

**两种检索配置都跑**：
- **真实检索**：走完整的服务链路，代表用户实际体验
- **隔离对照**：只跑关键词检索，用来判断"语义检索到底有没有带来增益"

## 4.2 评分指标

| 指标 | 含义 |
|---|---|
| Recall@K | 应找到的块里，前 K 名中出现了多少（查全率） |
| Precision@K | 前 K 名里有多少是相关的（查准率） |
| HitRate@K | 前 K 名里至少有一个相关块的比例 |
| MRR@10 | 第一个相关块出现在第几名的倒数（看排序质量） |
| nDCG@K | 综合考虑位置和相关等级（3 级的块排前面比 1 级排前面更好） |

**参数设定**：
- K 取值：1、3、5、10、20
- 二值化阈值：相关度 **≥ 2** 记为"相关"
- MRR 截断：前 10 名
- nDCG 增益：使用原始 0–3 等级，指数加权

## 4.3 无答案题的特殊评分

3 道无答案题不参与常规指标计算，单独衡量一件事：**系统是否返回了内容**。

- 正确行为：系统识别出资料库中没有答案，拒答
- 错误行为：系统硬凑出一个答案

这 3 道题考察的是**拒答机制的可靠性**，在科研场景里比"找到答案"更重要。

## 4.4 一个必须披露的技术约束

评测程序的默认设定是**严格模式**：如果检索结果里出现了"未判断过的块"，程序会直接报错退出。

这个设定在原方案（全量判定）下是合理的 —— 所有块都判断过，不会有遗漏。

但改为 pooling 之后，池外有 **295,708 个组合永远没被判断**。如果不放宽这个校验，绝大多数查询都会报错。

**所以采用 pooling 就必须同时放宽这项校验，代价是**：
- 被检索到但未判断的块，评分时**当作不相关**
- **召回率因此偏高**

这是 pooling 方案的固有代价，必须随最终指标一起披露，不能只报数字不提口径。

# 附：术语速查

| 术语 | 含义 |
|---|---|
| **RAG** | 检索增强生成 —— 先检索资料，再让模型基于资料回答 |
| **文本块（chunk）** | 论文被切分后的最小检索单位，本次平均约 2,000 字符 |
| **qrels** | 标准答案文件，记录每个"问题×文本块"组合的相关等级 |
| **Pooling** | 候选池方法：只标注各检索系统共同提名过的文档 |
| **池深度** | 每个系统提名前多少名进入候选池 |
| **未判断（UNJUDGED）** | 该组合没有标准答案，不等于"不相关" |
| **召回率（Recall）** | 该找到的相关内容里，实际被找到的比例 |
| **降级** | 语义检索不可用时退回纯关键词检索，并在结果中标注 |
| **拒答** | 资料库没有相关证据时，系统明确表示无法回答 |
| **OCR** | 光学字符识别 —— 从扫描图片中还原文字 |
