## 一、为什么调整范围

原方案要求标注整个 80 深度的候选池（8,252 对）。经核算，**评分真正需要覆盖的只有每个问题实际被评分的 Top-20**，加上已知正例。范围因此大幅收窄，而**深池完整保留、不作废**。

## 二、首版候选集（authoritative scope）

每题取以下并集：

1. **实际参与评分的 Top-20** —— 来自 **`runs.jsonl` 的 `results`**（`phase=formal` 且 `status=ok`）
   - **所有运行**：`http` 与 `isolated` 两轮
   - **所有重复**：每题 3 次 repeat **全部纳入**，不挑表现好的一次
2. **已知种子证据**（`seed_judgments.jsonl` 中 relevance ≥ 2）
3. **已有有效正例**（`qrels.tsv` 与 `judgments/*.json` 中 relevance ≥ 2）

> ⚠️ **口径来源**：`stages.jsonl` 只记录**各腿候选**，其 `note` 字段明确写着
> 「final post-filter Top-20 is in `runs.jsonl`」。早期用 `stages.jsonl` 估算会偏大。

## 四、深池保留，分阶段使用

- 原 Top-80 池及**全部已有结果保留，不删除**
- 首版**优先完成评分所需候选**
- 仅在遇到具体问题时，才从深池**定向补查**：
  - 可回答题却找不到有效正例
  - 跨文献证据不全
- **不统一要求**剩余所有深池候选立即完成

## 五、首版结果能说明什么（边界声明）

**可以**：比较本次冻结运行在**前 20 名**的表现。

**必须随结果披露的限制**：

| 指标 | 限制 |
|---|---|
| **Recall** | 解释为**相对于已知相关证据的召回率**，不是相对全语料的召回率 |
| **nDCG** | 理想排序依赖**当前已判断集合**，不声称全语料完备 |
| **新系统 / 新运行** | 出现未判断的 Top-20 结果时，**先补标再比较** |
| **未判断标签** | **保持未判断**，不得批量写成 0 |

### 首版验收要求

1. 所有**被评分的 Top-K 均有有效标签**
2. **已知证据已纳入**（种子正例 + 已有正例）
3. **明确的校验问题已解决**（ID 集合、字段类型、引文真实性）
4. **统计口径一致**

## 六、执行方式（当前可执行方案）

- 每批 **5 块**、**前台串行**
- 每批**独立路径**，落盘即校验
- 有效结果保留，**只处理失败项**
- 简单记录耗时与进度

> **这不是**「最佳批次大小」，只是当前可执行方案。若正例批次明显过长或反复失败，立即报告实际瓶颈，**不无限重试**。

**能力边界（勿夸大）**：
- 后台调度在本环境**未取得可查询句柄**，**未验证并发** —— 这不等于平台所有调用方式都无法并发
- 前台小批次**只能在批次之间停止**，**不能保证批次内部可取消或有硬超时**
- 5 块 51 秒是**单个全 0 级样本**，**不能据此承诺总体工期**

---

## 七、新增文献的增量方式

- **保留旧版本**；新版本跑既定检索配置后，对新增候选做**集合差分**
- 问题及限定条件、块正文与来源、适用规则**未变化**的有效判断 → **复用**
- **不**因新增文献而每题遍历全部新旧文本块，**不**重做全部旧标签
- **原无答案题必须重新检查**
- 其他变化按**实际受影响范围**处理

**目标：减少后续新增文献带来的新增标注量，而不是每次重做整套测评集。**
