# 测评集是怎么构建的 · 完整流程说明

**日期**：2026-09-17
**说明范围**：从"零"到"可用的检索测评集"的全过程

---

## 〇、先理解一件事：为什么这个过程绕不开"逐条判定"

普通考试有标准答案，阅卷很容易。**但检索测评没有现成的标准答案。**

要判断"检索系统返回的片段对不对"，必须先知道**哪些片段是对的**。这个"哪些片段能回答哪个问题"就是标准答案，也是整个测评集的核心产物。

**它只能一条一条判出来**，没有捷径 —— 这是全部工作量的来源。

---

## 一、整体流程（八步）

```
① 冻结文献库  →  ② 出题  →  ③ 跑检索  →  ④ 建候选池
                                              ↓
⑧ 交付成品  ←  ⑦ 机械校验  ←  ⑥ 逐条判定  ←  ⑤ 定判定规则
```

| 步 | 动作 | 产出 |
|---|---|---|
| ① | 冻结文献库 | 5,066 个可检索文本块 |
| ② | 出题 | 60 道题（带必需事实与参考答案） |
| ③ | 跑检索 | 每题的实际返回排名 |
| ④ | 建候选池 | **1,312 个"问题 × 片段"待判组合** |
| ⑤ | 定判定规则 | 4 级量表 + 判定流程 + 边界示例 |
| ⑥ | 逐条判定 | 每条组合的相关等级（**主工作量**） |
| ⑦ | 机械校验 | 校验报告 + 问题清单 |
| ⑧ | 交付 | 标准答案文件 + 说明文档 |

---

## 二、逐步说明

### 第 ① 步：冻结文献库 —— 确定"考什么资料"

**做什么**：从检索系统里，取出**官方作用域下可检索**的文献，锁定为一个不可变的快照。

**为什么**：
- 后续所有判定都基于这个快照，**必须可复现**
- 文献库一旦变动，之前的判定全部失效

**数字**：

| 项 | 数量 |
|---|---|
| 论文总数 | 51 篇 |
| **可检索论文** | **48 篇** |
| 页数 | 929 页 |
| 文本块总数 | 5,444 块 |
| **可检索文本块** | **5,066 块** |

> **为什么 5,444 → 5,066**：部分论文的页面因扫描质量或字符编码问题不合格，被**按页过滤**掉，而不是整篇丢弃。

**产出**：`corpus.jsonl`（5,066 个片段 + 来源、标题、页码等元数据）

---

### 第 ② 步：出题 —— 60 道题是怎么来的

**做什么**：**先在文献里找到一个"可验证的具体事实"，再围绕它设计问题。**

**举例**：
- 先在文献里找到：某实验"130°C 反应 30 分钟，糠醛收率 41.7%"
- 再设计问题：「在 2019 年 EMIMBr/SnCl4 体系中，130℃ 下木聚糖反应半小时的糠醛收率是多少？」

**为什么不凭空出题**：这样每道题天然带着"答案是依据哪段文献"，**不会出现题目本身有歧义、无法判定对错**。

**每道题携带的信息**：

| 字段 | 作用 |
|---|---|
| 问题原文 | 用户会怎么问 |
| **必须覆盖的事实** | 回答这题至少要说到哪几点 —— **判定相关等级的核心依据** |
| 参考答案 | 标准答案 |
| 题目指定来源 | 问题点名了哪篇文献（若有） |
| 题型 / 难度 / 语言 / 分区 | 用于分组分析 |

**60 道题的设计分布**：

| 维度 | 分布 |
|---|---|
| 语言 | 中文 42 / 英文 18 |
| 难度 | 简单 18 / 中等 30 / 困难 12 |
| 分区 | 开发 12 / 固定测试 36 / 挑战 12 |
| 题型 | 基础事实 9、条件参数 9、反应机理 9、定义概念 6、数据数值 6、对比分析 6、多文档综合 6、条件约束 3、语义改写 3、无答案 3 |

> **分区的用意**：开发集可随时看；固定测试集调参时**不许看**，用于最终客观评价；挑战集最难，单独统计以观察系统天花板。

> **"无答案题"的用意**：正确答案是"文献库里没有"。如果系统硬凑答案，说明拒答机制失效 —— 这在科研场景里是最危险的失败模式。

**产出**：`queries.jsonl`

---

### 第 ③ 步：跑检索 —— 拿到"系统会给出什么"

**做什么**：让检索系统对 60 道题**实际跑一遍**，记录每题返回的排名列表。

**为什么必须先跑**：标准答案要判"哪些片段能回答"，得先知道**系统会返回哪些片段**，否则无从判起。

**怎么跑**：

| 参数 | 设定 |
|---|---|
| 运行轮次 | 2 轮（真实检索 + 隔离对照） |
| 每题重复 | 3 次 |
| 单次超时 | 120 秒 |
| 合并方式 | 关键词检索 + 语义检索，融合排序 |

**跑出来的账**：

| 运行 | 计划 | 成功 | 失败 | 失败率 |
|---|---|---|---|---|
| 真实检索 | 180 | 149 | **31** | **17.2%** |
| 隔离对照 | 180 | 180 | 0 | 0% |
| **合计** | **360** | 329 | **31** | **8.6%** |

> **失败的 31 次单独记账**，不从分母消失；报告时单独披露失败率。

**产出**：`results/*/runs.jsonl`（每题每次的实际返回）

---

### 第 ④ 步：建候选池 —— 确定"到底要判哪些"

**这是最关键的取舍。**

**问题**：文献库有 5,066 个片段，60 道题。如果两两组合逐一判定，就是 **303,960 条** —— 不可能做完。

**做法**：只判**系统实际返回过的**那段。

```
每题取：所有检索运行 × 所有重复 × 实际返回的 Top-20 的并集
再加：已知的种子证据、已有的有效正例
```

**结果**：

| 口径 | 对数 |
|---|---|
| 逐一全判（不可行） | 303,960 |
| **首版候选集（采用）** | **1,312** |
| 其中已有标签可复用 | 62 |
| 其中需复核 | 384 |
| 其中**全新待标** | **866** |

**为什么这样是站得住的**：这是信息检索领域**三十年来的标准做法（pooling）** —— 如果一个片段真能回答某题，它大概率会被某个检索系统排进前列。遗漏的可能存在，但**对所有被比较的系统是一视同仁的**，不影响"哪个系统更好"的结论。

> **代价必须披露**：池外的片段永远没被判过，评测时按"不相关"处理，**Recall 会偏高**。这一点随结果一起披露。

**产出**：`coverage_scope.json`（每题要判哪些片段）

---

### 第 ⑤ 步：定判定规则 —— 4 级量表

**做什么**：定义"相关程度"怎么分档，写死判定流程。

**4 个等级**：

| 等级 | 含义 | 判定标准 |
|---|---|---|
| **3** | 精确命中 | 这一块**单独**覆盖问题所需的**全部必需事实** |
| **2** | 必要证据 | 只**部分**覆盖必需事实，需与其他块组合 |
| **1** | 有辅助价值 | 对回答这题有**可说明的**辅助价值，但不含任何必需事实 |
| **0** | 无关 | 与这题没有可说明的辅助关系 |

**判定流程（两级提问）**：

```
第 1 问：块里有没有问题要的那些必需事实？
    ├─ 全都有，一块能答     → 3 级
    ├─ 有一部分            → 2 级
    └─ 一项都没有          → 第 2 问
第 2 问：对回答这题有可说明的辅助价值吗？
    ├─ 有（能归入 5 类之一） → 1 级
    └─ 没有                → 0 级
```

**1 级的 5 类辅助价值**（必须归入其一，且理由要写清楚）：
同体系不同条件 / 同原料不同体系 / 同论文方法或数据 / 直接相关机理背景 / 不同论文的同类对照

**几条硬性规则**：
- 判 2/3 级必须摘录**该块内的连续原文**作为依据 —— **不能改写、不能跨块借用**
- **题目点名了具体文献时**（如"2018 年某综述列出…"），另一篇论文独立说了同样的事**只能判 1 级** —— 因为阈值是 ≥2，否则系统完全没找到指定文献也算命中
- 严格区分糠醛/HMF/CMF/乙酰 levulinic acid；木糖/木聚糖/葡萄糖/果糖；收率/选择性/转化率

**规范已冻结**（v4）：后续变更必须新建版本，不就地修改。

**产出**：`ANNOTATION_INSTRUCTIONS.md`

---

### 第 ⑥ 步：逐条判定 —— 主工作量在这里

**做什么**：对候选池里每一条"问题 × 片段"组合，给出 0/1/2/3 等级。

**怎么做**：
- 把一条题目的若干片段打成**小批次**（每批 5 个），每批携带**完整问题 + 必需事实 + 片段全文**
- 逐批判定，每批**独立落盘**
- 判定内容包括：等级、引文（2/3 级）、理由（0/1 级）

**谁来做**：**AI 助手**（不是人工专家）—— 这一点必须在交付时明确标注。

**速度实测**：

| 项 | 值 |
|---|---|
| 已完成 | 29 条 / 6 批 |
| 实际耗时 | 23 分钟 |
| **速度** | **1.26 条/分钟（76 条/小时）** |
| 单批（5 个片段） | 平均 3.8 分钟 |

**产出**：`gapfill/*/*.json`

---

### 第 ⑦ 步：机械校验 —— 防止"看起来完成"

**为什么必须做**：**条数对 ≠ 内容对。**

已经遇到的真实问题：
- 有一题**条数 138/138 完全对得上**，里面却混着一个**编造的片段 ID**
- 有 8 条引文**在整个语料里都不存在**（被改写或概括了）

**校验什么**：

| 检查项 | 说明 |
|---|---|
| 条数与 ID 集合 | 是否与候选池完全一致 —— 不多不少不重复 |
| 等级合法性 | 必须是 0/1/2/3 |
| **引文真实性** | **2/3 级的引文必须在该片段中逐字出现**（按四个层级判定，字形差异单独标记） |
| 必填字段 | 0/1 级必须有理由 |

**校验脚本自带自检**（14 项断言），可用于复现验证。

**产出**：校验报告 + 问题清单

---

### 第 ⑧ 步：交付

**产出物**：

| 文件 | 内容 |
|---|---|
| 标准答案（qrels） | 每条"问题 × 片段"的相关等级 |
| 文献快照 | `corpus.jsonl` |
| 题库 | `queries.jsonl` |
| 候选池 | `coverage_scope.json` |
| 标注与复核记录 | 逐条判断 + 修改历史 |
| 评测脚本 | 指标计算 |
| 测试报告 | 实际检索表现 |

**必须随交付披露的限制**：

- 标注为 **AI 生成**，非人工、非领域专家；**人工验收未完成**
- **池深有限**（Top-20），Recall 需解释为「相对于已知相关证据的召回率」
- 池外组合**保持未判断**，**不批量写成 0**
- **只能声明"首版范围完成"**，不能声明全部候选完成

## 三、三个关键设计决策（为什么这样做）

### 1. 为什么是 60 题而不是更多

题目数与判定量是**乘法关系**：每题候选约 22 条，60 题 = 1,312 条。题目翻倍，工作量直接翻倍。

60 题在**覆盖度与成本**之间取的平衡点：语言、难度、题型、分区都能铺开，同时判定量可控。

### 2. 为什么只判 Top-20 而不是全判

全判 303,960 条，**按当前实测速度需要约 4,000 小时**。取 Top-20 后降到 1,312 条，**约 16 小时**。

这个取舍有 TREC 三十年研究背书，代价（Recall 偏高）是已知且可披露的。

### 3. 为什么先跑检索再判定，而不是先判定再检索

如果先全判，就退回了"全判 30 万条"的老路。

**先跑检索**让我们知道"系统实际会返回什么"，判定范围因此收缩到 1/232。
