## 2. 已落实（对应审计第 2 条）★ 这条改变了一个失败桶的性质

**空 `zero_reasons` 现在合法当且仅当该题没有 0 级文档。** 两种编码规则一致：
- `parse_compact`：`zero_reasons` 允许短于题数，逐题只在「该题存在 0 级」时要求理由
- `parse_response`：`zero_reasons` 键集合允许是 qid 的子集，判据同上
- 同时把 perblock 的每文档理由改为**必需**（与 compact 的 per-proof 理由要求对齐）——是收紧不是放宽

**重算结果**：原先归入 `zero_reasons_count_mismatch` 的 2 条，放宽后**并没有变成通过**，而是暴露出真正的缺陷：`grades = ["122"]` 表示 doc0 也是 1 级（非零），但模型**没给 doc0 提供 proof**。所以它们正确地被判失败，只是失败原因换了桶。
> 结论：空理由是**误报的桶**，不是误判的样本。放宽规则增加了标签，没有增加错误标签。

**明确未做**：5 块只给 4 位等级时**不补位**。`"0000"` 的 `zero_reasons` 写了 `doc0,2,3 / doc1,4`（确实逐个看过），但「提到了全部 doc ID」不构成等级与文档对应的证明，仍判失败。

## 5. 断点与 1,130 条集合差分（对应审计第 5 条）

**断点判定已从「同名 JSON 是否存在」升级为「按唯一（题目,块）组合核对是否已有通过校验的判定」**（`scan_checkpoints` + `collect_judged_pairs`）。

这一改动**当场抓到一个真实问题**：`q_0001` 的 5 个批次与索引的块集合**逐批不等**（每批差 1–4 个 doc_id）。追查后确认：Agent 的 29 条与索引**覆盖同样的 24+5 个块，只是分批方式不同**（并集完全相同，交集 24/24、5/5）。所以：
- 若按批级判定 → 会把这 5 批误判为「未完成」并重跑，**白花 24 条已通过校验的标注**
- 按配对级判定 → 正确识别为已完成

**集合差分（全部按唯一 题目—块 组合计算）：**

```
1,312  首版候选集 = 实际评分 Top-20 并集 ∪ 种子正例 ∪ 已有正例（coverage_scope.py）
  182  可复用（判定通过当前规则，或 0 级规则未变）
1,130  验收缺口 = 1,312 − 182 = review_l1 135 + review_l23 164 + unlabelled 831
```
```

        索引待执行 pairs 与已落盘 pairs 的**交集 = 0**
```

**不重复扣除的证明**：1,312 − 1,250 = 62 = 索引按设计排除的「已判 0 级」块；这 62 与已落盘的 120 都包含在可复用的 182 内，因此 `1,250 − 120 = 1,130` 与 `1,312 − 182 = 1,130` 是同一个集合的两种算法，不是两次扣减。
（旧快照「可复用 91」是 1,221 缺口时期的读数，与本次 182 不同期，不构成重叠。）
