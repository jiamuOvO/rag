## 一、项目目标

### 要回答的问题

**「这套 RAG 检索系统，在真实的科研文献问答上，到底好不好？」**

要回答它，必须有一个**带标准答案的考卷**。这个文件夹就是在造那份考卷。

### 为什么不能直接看问答效果

RAG 问答最终输出的是一段话，掺了生成模型的发挥。想单独衡量**检索**这一环，必须：

1. 固定一批问题
2. 固定一个文献库
3. 说清楚**每个块对每道题的相关程度**（这就是标准答案，行话叫 qrels）
4. 拿检索系统返回的结果去比对

第 3 步是全部工作量所在 —— 也是这个项目的核心。

### 对象与范围

| 项 | 内容 |
|---|---|
| 领域 | 生物质转化 / 呋喃化学（糠醛、HMF、乙酰丙酸、CMF、FDCA 等） |
| 语料 | 生产库里**官方作用域**下可检索的论文块 |
| 问题 | 60 道中文/英文科研问答，题目由已有证据反推设计 |
| 产出 | 可复现的 qrels + 评测脚本 + 真实检索基线 |
| 不测什么 | **不测生成质量**。只测检索有没有把该找的块排上来 |

## 三、核心方法：为什么用 Pooling

### 两条路的差别

| | 全量判定 | **Pooling（本项目采用）** |
|---|---|---|
| 每题看多少块 | 5,066（全部） | 137（系统推的） |
| 总判断次数 | 303,960 | **8,252** |
| 完整性 | 完备 | 池外记 UNJUDGED |
| 依据 | 理论最强 | **TREC 1990 年代至今的标准做法** |

### 为什么全量不可行

TREC-12 官方文档给的数字：800,000 篇文档，全量判定每题需要 **6,500 小时**（按 30 秒/条）。这是 TREC 当初发明 pooling 的原因。

### Pooling 的代价（必须披露）

- **池外的组合永远没被判断**，评测时按"不相关"处理
- 后果：**Recall 会偏高**（分母少算了潜在的相关块）
- 缓解：池深度挖到 80（见下），且评审时披露池深度

### 池来源与深度

从两轮已完成的真实检索运行合并去重：

| 运行 | 目录 | 系统 | 每题深度 |
|---|---|---|---|
| HTTP 真实检索 | `results/http-20260916T063408115501Z` | bm25 | 80 |
| 同上 | | dense | 80 |
| 同上 | | rrf | 20 |
| 隔离 BM25 对照 | `results/isolated-20260916T064442079079Z` | bm25 | 80 |

> **注意区分两个 top**：`top_k=20` 是**算指标**时的截断；**池深度 80** 是建池时挖到多深。两者用途不同，不要混。

**当前池深度 80，低于 TREC 惯例（100–200）。** 这是已知限制，两种处理方式：接受并披露，或后续重跑一轮加深。

### ④ 建池

```bash

```

- **输入**：两轮 `stages.jsonl`
- **规则**：取所有运行中出现的全部候选，按「题 × 块」合并去重；保留每块在各系统中的**最佳排名**
- **输出**：`pool.jsonl`（60 行，每题一行）
- **结果**：**60 题 / 8,252 对 / 每题 107–161 块**
- **自检断言**：题目数 == 60、每题池大小在 (0,500)、总量在 (1000,20000)

### ⑤ 生成标注任务文件

```bash
python -B tests/biomass_furan/make_task_files.py
```

- **输入**：`pool.jsonl` + `corpus.jsonl`
- **输出**：`tasks/q_XXXX.txt`（60 个）
- **关键处理**：把 PDF 换行压平后硬折到 **1800 字符/行**，行数从 6,069 降到 **411–580**
- **为什么**：Read 工具会截断超过 2,000 字符的行、每次最多读 2,000 行。不处理会导致块被**静默截断**，标注随之失真

### ⑥ 标注

**规范文件**：`ANNOTATION_INSTRUCTIONS.md`（**必须原样使用，不要简化**）

**等级定义**（4 级，与 TREC Deep Learning / UMBRELA 一致）：

| 等级 | 含义 |
|---|---|
| **3** | 这一块**单独**就能给出问题所需的全部/大部分核心事实 |
| **2** | 含**必要的直接证据**，但需与其他块组合才能完整回答 |
| **1** | 讨论**同一研究对象/体系/论文的相邻内容**，提供背景、对照、方法，但本身不含所问证据 |
| **0** | 与该问题**主题不同**（不同化学品、不同工艺路线、不同领域） |

**判定流程**（两级提问，决定等级）：

```
第 1 问：讲的是不是本题涉及的对象/体系/论文？
         否（换了主题）→ 0 级
         是            → 继续
第 2 问：有问题所问的具体数值/事实吗？
         有，一块就能回答 → 3 级
         有，需组合       → 2 级
         没有，只是背景   → 1 级
```

**硬性要求**：

- 池内**每一个块都要给等级**，条数必须与 `pool_size` 一致
- 判 **2/3 级必须给 `evidence_quotes`** —— 从**该块内部**摘录的连续原文，不能跨页借用、不能凭知识补写
- **0 级必须给 `reason`**，且理由必须说明"为什么主题不同"，不能写"关键词未命中"
- 严格区分 furfural / HMF / CMF / 乙酰丙酸；xylose / xylan / glucose / fructose；yield / selectivity / conversion

**输出**：`judgments/q_XXXX.json`

```json
{"query_id": "q_0003", "judgments": [{"doc_id": "chk_...", "relevance": 0, "evidence_quotes": [], "reason": "..."}]}
```

> **实操教训**：第一版指令只给等级定义时，执行者会把分级做成"有没有答案"的二分类（135 块里 133 个 0 级、**1 级为 0**）。加上「判定流程」和「1 级/0 级边界示例表」后，1 级从 0 变为 89。**给分级标注写指令，必须给每个等级的边界例子。**

## 六、评分口径（`evaluate.py`）

| 项 | 设定 |
|---|---|
| K 值 | 1 / 3 / 5 / 10 / 20 |
| 二值化阈值 | relevance ≥ **2** 记为相关 |
| MRR 截断 | 10 |
| nDCG 增益 | 使用**原始 0–3 标签**，指数增益 |
| 排名依据 | **首次正式运行的存盘排名** |
| 延迟 | 每题 3 次的**中位数** |
| 报告方式 | 成功 / 降级 / 失败**分别报告** |

> qrels 不完整时脚本**默认阻止正式评分**。不得用 `--provisional`（未判断按 0）的产物冒充最终指标。

### ⚠️ Pooling 对评分脚本的直接影响（关键，已核对代码）

`evaluate.py:52` 的 `score_query()` 默认 `allow_unjudged=False`：

```python
if not allow_unjudged and any(did not in qrels for did in ids):
    raise ValueError('Unjudged returned document')
```

一旦检索结果里出现**池外未判断的块**，评分**直接抛异常**。

走 pooling 后池外有 295,708 个组合永远没被判断，所以**评分必须显式传 `allow_unjudged=True`**，否则绝大多数查询会报错退出。

**代价（必须随指标一起披露）**：

- 被检索到但未判断的块按 `qrels.get(doc, 0)` 处理，即**当作不相关**
- **Recall 因此偏高**（分母少算了池外的潜在相关块）
- nDCG 中池外块的增益记 0

> 这也解释了原方案为什么坚持全量判定 —— 全量 qrels 才能让 `allow_unjudged=False` 这条严格校验继续成立。选 pooling 就等于**同时接受了这项校验的放宽**。
